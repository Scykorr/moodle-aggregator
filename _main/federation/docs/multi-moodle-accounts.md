# Несколько Moodle на разных адресах: пошаговая работа и учётные записи

Подробная операционная инструкция. Рассчитана на Moodle **4.x и выше**
(также подходит 3.3+ со встроенным OAuth 2) в разных подсетях/по разным URL.

Связанные документы: [operator-guide.md](operator-guide.md),
[deployment.md](deployment.md), [migration.md](migration.md),
[architecture.md](architecture.md).

---

## 1. Как это устроено (сначала понять модель)

Работают **два независимых** Docker-стека плюс ваши Moodle:

```text
Администратор сети          Студент
        │                      │
        ▼                      ▼
  Агрегатор (:8090)      Keycloak (:8443)
  список URL Moodle      один логин / пароль
  проверка доступности         │
        │                      │ кнопка «Единый аккаунт»
        │                      ▼
        └──────────►   Moodle A / B / C (разные IP/URL)
                       локальные курсы, оценки, user.id
```

| Вопрос | Ответ |
|---|---|
| Где «настоящий» аккаунт студента? | Только в **Keycloak** (realm `students`) |
| Синхронизирует ли агрегатор учётки? | **Нет.** Агрегатор — каталог площадок и проверка HTTP(S) |
| Копируются ли пароли между Moodle? | **Нет** |
| Нужно ли регистрироваться на каждом новом Moodle? | **Нет** — один раз в Keycloak, дальше кнопка SSO |
| Что появляется в Moodle при первом SSO? | Локальный профиль (`user.id`) для курсов и оценок |
| Общий каталог курсов / общие оценки? | **Нет** в этой схеме — только единый вход |
| Связка «это тот же человек» | Поле Keycloak `sub` → username OAuth-сервиса Moodle |

**Не заводите** студентов сначала на Moodle «чтобы потом собрать в агрегатор» —
дубли и конфликты email/логинов неизбежны. Источник истины — Keycloak.

## 2. Что должно быть готово до студентов

### 2.1. Инфраструктура

1. Docker Desktop Running на хосте федерации.
2. Агрегатор: http://127.0.0.1:8090 (или LAN IP из `.env.aggregator`).
3. Keycloak: https://127.0.0.1:8443 (или боевой `idp_url`).
4. С каждого студенческого ПК и из PHP каждого Moodle доступны:
   - HTTPS Keycloak по каноническому имени/URL;
   - HTTPS каждого Moodle по его `$CFG->wwwroot`.

Офлайн-перенос стеков: [offline-aggregator.md](offline-aggregator.md),
[offline-keycloak.md](offline-keycloak.md).

### 2.2. Инвентаризация Moodle (агрегатор)

1. Откройте **публичный** каталог: http://127.0.0.1:8090 — так его видят студенты.
2. Админка структуры: http://127.0.0.1:8090/admin (пароль, если задан `AGGREGATOR_TOKEN`).
3. Создайте **факультеты** (без URL Moodle) и **кафедры/площадки** с адресами.
   Кафедру можно оставить «без факультета» или перетащить в факультет.
4. «Проверить Moodle» в админке — для строк с адресом.
5. Зафиксируйте таблицу вручную при необходимости (вне Git, если там внутренние IP):

| id | Версия | IP | Подсеть | Канонический HTTPS URL (`wwwroot`) |
|---|---|---|---|---|
| moodle4a | 4.5.x | 10.40.0.10 | 10.40.0.0/24 | https://moodle4a.example |
| moodle4b | 4.1.x | 10.40.0.20 | 10.40.0.0/24 | https://moodle4b.example |
| moodle5 | 5.2.x | 10.50.0.10 | 10.50.0.0/24 | https://moodle5.example |

У каждого Moodle `$CFG->wwwroot` **должен совпадать** с URL, по которому заходят
студенты и с redirect URI в Keycloak. HTTP без TLS для боевого SSO не подходит.

Студент на портале выбирает факультет → карточку кафедры → переход в Moodle.
Учётки по-прежнему только в Keycloak (см. разделы ниже).

### 2.3. Реестр SSO (`sites.json`)

На машине с Python в `_main/federation`:

1. Скопируйте `sites.example.json` → `sites.json` (или отредактируйте существующий).
2. Заполните реальные `url`, `ip`, `subnet`, `version`, уникальные `id`.
3. `idp_url` и `bind_ip` — адрес хоста Keycloak (без пути в URL).
4. Проверка:

```powershell
python prepare.py --validate-only
```

5. Если Keycloak ещё не поднимали впервые:

```powershell
python prepare.py
# certs/ уже должны быть
docker compose --env-file generated/.env up -d --pull never
```

Секреты клиентов: `generated/moodle-settings.md`.  
**Если realm уже импортирован**, повторный `prepare.py` не добавит новые сайты —
для нового Moodle клиент создаётся вручную в Keycloak (шаг 4 ниже).

## 3. Подключение каждого Moodle к Keycloak (один раз на сайт)

Повторите для **каждого** адреса из таблицы.

### 3.1. Клиент в Keycloak

В консоли https://…/admin → realm **`students`** → Clients:

1. Create client → Client ID = значение `id` из реестра (например `moodle4a`).
2. Client authentication: **On** (confidential).
3. Authentication flow: только **Standard flow** (Authorization Code).
4. Direct access grants: **Off**.
5. Valid redirect URIs — ровно одна строка:
   `https://<wwwroot-этого-Moodle>/admin/oauth2callback.php`
6. Web origins: пусто или строго по политике.
7. Client scopes по умолчанию: `profile`, `email` (и openid).
8. Credentials → скопируйте **Client secret** в безопасное место.

### 3.2. OAuth 2 в Moodle

Под локальным админом Moodle:

1. Администрирование сайта → Сервер → **Сервисы OAuth 2**.
2. Создать сервис (Custom):
   - название на странице входа: **Единый аккаунт**;
   - Client ID / secret — из Keycloak для **этого** сайта;
   - Service base URL: `https://<idp>/realms/students`  
     (пример стенда: `https://127.0.0.1:8443/realms/students`).
3. Включить показ на странице входа.
4. Scopes: `openid profile email`.
5. Проверить discovery / endpoints (auth, token, userinfo).
6. Сопоставление полей пользователя:
   - `sub` → **username**
   - `given_name` → firstname
   - `family_name` → lastname
   - `email` → email  
   Удалите конфликтующие mapping на username.
7. Плагины → Аутентификация → включить **OAuth 2**.
8. **Не отключайте** аварийный локальный вход администратора.
9. На этапе пилота связанных входов: запретите автосоздание пользователей
   через OAuth (см. [migration.md](migration.md)); после пилота — разрешите
   создание при первом SSO для новых студентов.

Проверка кнопки: выход → страница входа → «Единый аккаунт» → редирект на Keycloak
→ возврат в Moodle без ошибки callback.

## 4. Как заводить учётные записи

### 4.1. Новые студенты (основной путь)

1. Keycloak → realm `students` → **Users → Add user**:
   - Username (стабильный учебный идентификатор, не менять потом);
   - Email — уникальный и реальный;
   - First / Last name;
   - Email verified = Yes (или подтверждение через SMTP).
2. Credentials → Set password (temporary = Yes → смена при первом входе).
3. Саморегистрацию в Keycloak **не включайте** (в шаблоне выключена).
4. Саморегистрацию по email в каждом Moodle **отключите**.
5. Студент:
   - открывает любой подключённый Moodle;
   - жмёт **Единый аккаунт**;
   - входит логином/паролем Keycloak;
   - при первом заходе Moodle создаёт локальный профиль сам.
6. Зачисление на курсы — обычными средствами этого Moodle (вручную, когортами,
   метакурсами и т.д.). SSO курсы не копирует.

Переход на второй и третий Moodle: снова кнопка «Единый аккаунт».  
Если сессия Keycloak ещё жива — пароль часто не спрашивают повторно.

### 4.2. Студенты, которые уже есть в Moodle (сохранить оценки)

Не создавайте им «вторую» запись SSO вслепую — сначала **привязка**.

Краткий пилот (детали: [migration.md](migration.md)):

1. Бэкап Moodle.
2. Заведите тех же людей в Keycloak (по утверждённому реестру, не «похожему ФИО»).
3. В Moodle на время пилота: OAuth **без** автосоздания пользователей.
4. Студент входит **старым** способом → Настройки → **Связанные входы** →
   добавить «Единый аккаунт» → подтвердить вход в Keycloak.
5. Выйти → войти только через SSO → проверить: тот же `user.id`, курсы и оценки
   на месте, дубля нет.
6. После успеха на пилоте — тираж; затем разрешить автосоздание для совсем новых.

Запрещено: SQL-привязка «по совпадению email», общий семейный email как ключ,
перенос хешей паролей из Moodle в Keycloak.

### 4.3. Преподаватели и админы Moodle

- Обычные преподаватели — как студенты (Keycloak + при необходимости Linked logins).
- Технические локальные админы Moodle — оставить локальный вход на случай аварии IdP.
- Админов Keycloak: после настройки создать постоянного администратора с MFA,
  не жить вечно на `bootstrap-admin`.

## 5. Повседневный цикл работы с несколькими адресами

### Утро / смена администратора сети

1. Агрегатор → «Проверить все» — все боевые Moodle зелёные/доступны.
2. Keycloak admin → Users: при необходимости завести новых студентов.
3. Новый Moodle в сети:
   - строка в агрегаторе;
   - клиент в Keycloak + OAuth в Moodle (раздел 3);
   - пилотный вход одного тестового пользователя.

### Студент учится на трёх Moodle

1. Аккаунт один — в Keycloak.
2. На Moodle A, B, C — три локальных профиля, связанные одним `sub`.
3. Оценки A не видны в B автоматически.
4. Блокировка в Keycloak → нельзя начать новый центральный вход; уже открытые
   сессии Moodle проверяйте отдельно (см. матрицу в migration.md).

### Блокировки и отзыв доступа

| Действие | Эффект |
|---|---|
| Disable user в Keycloak | Новые SSO-входы запрещены |
| Suspend в конкретном Moodle | Нет доступа к этому сайту даже через SSO |
| Удалить клиента Moodle в Keycloak | Этот сайт перестанет принимать SSO |

## 6. Добавление ещё одного Moodle (чеклист)

- [ ] HTTPS и корректный `wwwroot`
- [ ] Строка в агрегаторе, проверка зелёная/приемлемая
- [ ] Запись в рабочий инвентарь / `sites.json` (`--validate-only`)
- [ ] Confidential client в Keycloak + уникальный secret + точный callback
- [ ] OAuth 2 сервис «Единый аккаунт» в Moodle, mapping `sub → username`
- [ ] Пилот: новый пользователь Keycloak входит на этот Moodle
- [ ] Если есть старые локальные учётки — Linked logins на 2–3 пилотах
- [ ] Саморегистрация Moodle выключена; зачисления настроены отдельно

---

## 7. Чего делать нельзя

1. Хранить студентов «в агрегаторе» или общей БД пользователей всех Moodle.
2. Считать одинаковые ФИО/email доказательством одного человека без реестра.
3. Менять `sub` / username Keycloak после привязок (сломает связи).
4. Переиспользовать один client secret на несколько Moodle.
5. Указывать в redirect URI `*` или чужой `wwwroot`.
6. Отключать всех локальных админов Moodle до проверки аварийного входа.
7. Обещать единый logout сразу со всех Moodle — поведение проверяйте отдельно.

## 8. Краткая шпаргалка адресов стенда

| Сервис | URL |
|---|---|
| Каталог (студенты) | http://127.0.0.1:8090 |
| Админка каталога | http://127.0.0.1:8090/admin |
| Keycloak | https://127.0.0.1:8443 |
| Admin Keycloak | https://127.0.0.1:8443/admin |
| Логин bootstrap | `bootstrap-admin` (пароль в `generated/.env`) |
| Секреты OAuth | `generated/moodle-settings.md` |

На боевой сети замените адреса на LAN/`idp_url` из вашей конфигурации и
раздайте доверие к внутреннему CA на клиентах и в контейнерах Moodle.
